## 二、四个新方向详述

### 方向 6 · 麦探长（原「跨店套利雷达」→「同城觅食雷达」，2026-10-13 定名，已按实测数据修正）

**一句话**：麦探长——跑遍全城的麦当劳物价侦探。所有省钱项目都只算「最近的一家店」；它把附近 N 家店全部巡查一遍，输出价差榜 + 可得性提醒，每条线索都可查。

**人设与产品的同源性**（命名理由）：侦探=「办每案都留证据」的职业，与麦探长「过程可查、不装」的产品 DNA 一致——巡查=扫门店、线索=每条 MCP 返回、证物=原始 request/response、报案=用户需求、结案报告=结果卡、悬案=诚实降级（今日各店同价，无从比起）。名字即定位，不需要副标题解释。命名备选还有「麦罗地图/麦价情报站/寻麦记/麦门巡按使」，定「麦探长」的理由：不透支 UI（不承诺地图）、人设可延展（热量审计署=健康档案室、省钱打假=证物科、团餐=团体报案，一个 IP 串起 README Roadmap）。仓库 slug 保持朴素（`mcd-city-detective` 或 `mcd-price-scout`），中文名负责传播、英文名负责检索。

**核心机制**（七步，全部只读）：
1. `query-nearby-stores` 拉用户位置附近**全部**门店（不只最近一家，默认取 3–5 公里内前 N 家，N 可配）；
2. 对每家门店分别 `query-meals`（可售菜单）+ `query-store-coupons`（门店券）；
3. 归一化：同一餐品编码跨店对齐，标注「本店无此餐品」而非静默丢弃；
4. 用户给一餐目标（如「麦辣鸡腿堡套餐」）→ 对每家店分别组合定价 + `calculate-price` 核价；
5. 外送场景叠加 `delivery-query-stores`（beType=2）的配送费与可配送范围（**配送费差异目前仅 n=2 样本、未证实，标 UNVERIFIED**）；
6. 输出「各店总价排行 + 差价归因」+「你想吃的只有 X 店有」可得性提醒；
7. 全程 trace 化：每店一条子证据链，点开可核验。

**实测依据（2026-10-13，30 店 6 城，脚本可复现，详见 `CONTEST_PRICE_PROBE_2026-10-13.md`）**：
- 菜单价差：一线/新一线城市共同单品中 **22%–46% 有跨店价差**（上海 22.0% / 武汉 23.2% / 北京 27.1% / 深圳 33.3% / 成都 45.8%），**中位价差 0.5–1 元/单品**；三线城市罕见（黄冈 3.8%）
- 餐品可得性：同城共同单品覆盖率仅 **36%–76%**——「想吃的那款别家才有」比价差更高频
- **门店券同城高度一致**（6 城中 5 城完全相同）——券维度无套利空间，此前的假设已修正
- 成都 8 元极端价差来自「快捷小站」特殊店型，非普遍现象

**榜单差异化**：0 个多门店项目。省钱类（coupon-strategist 256★ 等 9 个）全部单店。

**Star 传播逻辑**：用**真实数据**做钩子——「同城同餐差 3 块」（北京精选单人餐三件套 33.5 vs 36.5 实测）+ 「跑了 3 家店才吃到」；README 直接放 30 店探测数据与可复现脚本，比编造 demo 有说服力。

**麦探长资产复用**：高。多门店 = 并行多 trace，恰好展示「每店价格可戳开核验」；事件流可做成「探长巡查直播」动效。

**风险与诚实边界**：① 单次快照，价差可能随时段/活动变动，输出须带探测时间戳；② 没差异就如实说「今日各店同价」，不制造假价差；③ 识别特殊店型（快捷小站等）并单独标注；④ 注意 600 次/分钟限流，控制并发；⑤ 期望收益按真实幅度管理（一餐 1–3 元），不做「省一半」式宣传。

**工作量**：中（主逻辑是已有 pipeline 的多门店并行化）。

### 方向 7 · 企业团餐管家 ——「行政小姐姐的救星」

**一句话**：6 个派对项目全是家庭 C 端场景；企业团餐有 MCP 独占工具，却没人做。

**核心机制**（诚实版，含能力边界）：
1. `query-meal-assistance` 确认目标门店支持的企业团餐/助餐服务（**该工具仅企业团餐场景可用**，官方描述原文）；
2. `query-meals` + `query-meal-detail` 拉可配置菜单（含套餐更换组合、餐品特制能力，v1.0.5 起支持）；
3. 输入「人数 / 人均预算 / 忌口清单」→ 生成配置方案：品类搭配、忌口规避、超预算项红灯；
4. `calculate-price` 对方案整体核价，输出「人均价 + 总价 + 超支项」；
5. 输出一份**可转发的配置单**（给同事确认用），trace 记录「谁提的忌口、哪项被规避」；
6. **诚实边界：MCP 工具面暂无「企业团餐下单」工具**（`create-order` 是个人点餐、`party-order-create` 是主题活动/派对向）——最终步明确标注「凭本配置单联系门店或企业团餐通道办理」，不假装能一键下单。

**榜单差异化**：0 个 B 端项目。行政/HR 是技术社区活跃人群，「行政的救星」人设清晰。

**Star 传播逻辑**：痛点真实（行政订团餐靠 Excel 和电话）；「AI 帮我给 50 人订餐」截图传播；B 端场景在 C 端向的榜单里反而显眼。

**麦探长资产复用**：高。团餐是多步长链路，trace 证据链价值最大（每一项忌口规避、每一笔核价都可戳开）。

**风险与诚实边界**：见机制第 6 步——不能假装有团餐下单能力；单人 Skill 形态做「收集多人忌口」需轻量设计（配置单分享 + 手工汇总），不硬做协作系统。

**工作量**：中高（新场景流水线，但可复用 pipeline 骨架）。

### 方向 8 · 麦金卡 ROI 精算师 ——「麦当劳求着我开卡，我让 AI 算了一笔账」

**一句话**：省钱项目算「这一单怎么点最便宜」；它算「会员卡这一年的订阅值不值」——决策类型完全不同。

**核心机制**：
1. `order-list` 拉取历史订单（官方口径为「近期」订单，**具体时间范围 UNVERIFIED**，以实际返回为准并写进输出）；
2. 从订单中归纳消费模式：月均单数、客单价、早餐/正餐/外送占比、常用门店；
3. 对比麦金卡/早餐卡的开卡成本 vs 按该消费模式可获得的权益价值（v1.0.6 起支持随单购买，**权益细则 MCP 无查询工具，权益参数由用户配置或标注以官方为准**）；
4. 输出结论卡：「按你过去 N 单的消费，开卡预计年省 ¥X / 持平 / 不值」；
5. 敏感性分析：如果每月多叫一单外送、如果早餐频率翻倍——开卡价值怎么变（一张小表）；
6. 全程 trace：每笔订单如何被归类、每项权益如何计价，全部可戳开。

**榜单差异化**：0 个。积分类 8 个做「盘点」，省钱类做「单次」；「订阅制 ROI」是空档，且与麦金卡这个真实付费产品强绑定。

**Star 传播逻辑**：反向叙事（「AI 教我别开卡」）比「帮你省钱」更有记忆点；ROI 结论数字天然可传播。

**麦探长资产复用**：高（历史订单分析 = trace 化呈现的强场景）。

**风险与诚实边界**：①「近期」订单范围未定义，ROI 只能基于**实际拉取到的数据**计算，范围必须显式写出；②会员卡权益细则无 MCP 工具支撑，参数需透明可改；③结论措辞保守（「按历史数据的估算」），不做保证。

**工作量**：中。

### 方向 9 · 抽奖期望值实验室 ——「抽奖前，先让 AI 给你泼盆冷水」

**一句话**：抽奖域（v1.0.8 上线）有独占工具、0 人做；它把抽奖当概率题来算，而不是当手气来赌。

**核心机制**：
1. `query-my-account` 拿可用积分；`query-lottery-info` 拉当前抽奖活动的奖品列表、单次消耗、中奖规则（**活动是否常驻 UNVERIFIED**）；
2. `mall-points-products` + `mall-product-detail` 拉商城可兑换商品，建立「积分的实物价值基准」；
3. 计算单次抽奖的**期望收益**（Σ 奖品价值 × 概率）vs 消耗的积分按商城价折算的价值；
4. 输出结论：「当前活动抽奖期望值 ¥X/次，同积分商城直换价值 ¥Y——抽奖（划算/不划算/持平）」；
5. 教育向包装：把概率算给用户看（「你以为在赌运气，其实每题都有答案」）；
6. **降级路径**：当期无抽奖活动时，自动切换为「积分商城最优兑换顾问」——按即将过期积分优先、价值密度排序推荐兑换组合；
7. **`draw-lottery` 是写操作，默认不执行**，只在用户显式要求时才提示可手动执行。

**榜单差异化**：0 个。抽奖是 2026-08 才上线的新能力，窗口期红利；「赌场数学」话题在技术社区有天然受众。

**Star 传播逻辑**：「抽奖是智商税吗？我让 AI 算了期望值」——反直觉结论驱动传播；与「积分盘点」类形成鲜明智识差。

**麦探长资产复用**：中（概率计算是新模块，但 trace/证据链可直接用）。

**风险与诚实边界**：合规是最大项——**只做期望值透明化，不诱导抽奖**，UI 文案明确「本工具不鼓励博彩行为」；活动非时常驻，降级路径必须真实可用而非空壳。

**工作量**：低-中。

## 三、五方向对比与推荐

| 维度 | 热量审计署 | 麦探长 | 企业团餐管家 | 麦金卡 ROI | 抽奖期望实验室 |
|---|---|---|---|---|---|
| 直接竞争 | 8 个近似 | 0 | 0 | 0 | 0 |
| 传播钩子强度 | 高（健康焦虑） | 高（实测价差 + 可得性） | 中高（B 端痛点） | 高（反向叙事） | 高（反直觉） |
| 麦探长资产复用 | 中 | 高 | 高 | 高 | 中 |
| 工作量 | 中 | 中 | 中高 | 中 | 低-中 |
| 合规/数据风险 | 中（健康边界） | 低 | 中（不能假装能下单） | 中（权益参数透明） | 中（不诱导博彩） |
| 依赖新模块 | 营养匹配 | 多门店并行 | 忌口引擎 | ROI 模型 | 概率模型 |

**推荐组合：麦探长 + 热量审计署 双主线，团餐管家做 B 端差异点，ROI 与抽奖做 README 彩蛋场景。**

理由：
1. **双主线覆盖两大流量叙事**：省钱（已被 256★ 验证的最大需求）× 健康（永恒话题），且两者都是 0 直接竞争——麦探长打空间维度，审计署打时间维度，互不重叠；
2. **两个都能最大化复用麦探长资产**（并行 trace / 历史订单 trace），12 天工期现实；
3. **麦探长的价差已实测验证**（2026-10-13，30 店 6 城：一线/新一线 22%–46% 共同单品有跨店价差、共同单品覆盖率仅 36%–76%；门店券同城高度一致，券维度无套利），不是拍脑袋方向——但叙事按真实幅度设计（一餐 1–3 元），「诚实扫描」本身即差异点，详见 `CONTEST_PRICE_PROBE_2026-10-13.md`；
4. **团餐管家写进 Roadmap 展示 B 端野心**——「行政的救星」人设稀缺，且 query-meal-assistance 是独占能力，先占位；
5. **ROI 与抽奖作为「彩蛋场景」**放 README，成本低话题足，冲 Star 用；
6. 与 V1 的关系不变：方向 1「麦麦不装」仍是报名本体（证据链是上述五个方向共用的底座——每个方向的结论都该可戳开核验），方向 2「省钱打假」的传播素材可升级为「同城扫描 + 证据链」的复合形态。
